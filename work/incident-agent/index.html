Incident Intelligence Agent — alert to drafted RCA in under ten seconds.

Open-source incident-triage agent informed by the production work I do at Orangetheory Fitness. Takes a raw alert, retrieves the most similar past incidents from a local vector knowledge base, and drafts a root-cause analysis in markdown a human can paste straight into Jira or Slack.

latency< 10 seconds end-to-end lineagebuilt at Orangetheory Fitness stackClaude API · ChromaDB · Python repogithub.com/shans15/incident-intelligence-agent

Problem

The first ten minutes of an incident response are spent on two things that have very little to do with actually fixing the problem: writing the RCA structure from scratch ("Summary / Impact / Timeline / Probable Cause / Mitigation / Action Items") and hunting through Slack, Confluence, and old Jira tickets for "didn't we hit something like this last quarter?"

Both are retrieval problems disguised as writing problems. The RCA structure is templated. The "have we seen this before" search is bounded — it's not the open web, it's your own incident history. On-call engineers waste 30–60 minutes per incident on work that a small, well-scoped system can do in seconds, freeing the human to focus on the actual remediation.

Constraints

  • Latency budget under ten seconds. Anything longer and the engineer has already started writing the RCA themselves; the agent's output gets ignored.
  • Local-first retrieval. The vector knowledge base is local to the deployer's environment. Past incident text is sensitive — the agent can't be a "send your incidents to a cloud vector DB" product.
  • Output must be paste-ready. No "click here to view the full report" indirection. The output is markdown the engineer drops into Jira and finishes editing in seconds.
  • Vendor neutral. The OTF version of this work runs against an enterprise on-call stack. The open-source version explicitly avoids vendor lock-in — Claude is the default but the interface is model-agnostic, ChromaDB is the default but the retriever is pluggable.

Approach

Same three stages, applied to alerts instead of patients or tickers.

01 / Signal — normalize the inbound alert

Alerts come in two forms: PagerDuty JSON payloads or plain text (a Slack message, a copy-pasted email). The first step is a tiny normalization layer that pulls service name, severity, error class, and timestamp into a structured form the rest of the pipeline can reason about. Bad alerts get rejected here — empty payloads, malformed JSON — before any model call.

02 / Rank — retrieve similar incidents from a local vector KB

The local ChromaDB is seeded with past incident reports, postmortems, and runbook entries. The normalized alert is embedded and a top-K similarity search returns the most relevant past incidents along with their distances. K is small — typically 3–5 — because the downstream LLM call has a token budget and the retrieved snippets need to fit inside it.

This is the part of the system that has to be local. Past incidents are the highest-value institutional knowledge an engineering team has; they don't leave the environment.

03 / Explain — drafted RCA with cited precedents

The retrieved incidents go to Claude (with retry and exponential backoff for production resilience) along with the normalized alert and a structured RCA prompt. The output is markdown with the standard RCA sections, plus an explicit "Similar past incidents" section that cites the retrieved precedents by ID and explains why each is relevant.

The "Explain" property is what separates this from a generic "summarize my alert with an LLM" wrapper. The engineer doesn't just see a draft; they see why this draft — which past incidents informed it, and where to go look for additional context.

The OTF lineage

I architected a similar system in production at Orangetheory Fitness. The open-source agent in this repo is the vendor-neutral expression of that work — the same architectural shape (alert → local vector retrieve → LLM RCA draft with cited precedents), rebuilt with public components so anyone can run it.

The lineage matters because production deployment teaches things side projects don't. Retry policies. Token budget overflow handling. The need for an explicit "skip this incident" path when the alert payload is junk. The realization that the engineer trusts the draft more when it cites the prior incidents than when the LLM output looks too polished. All of those decisions are in the OSS version because they were learned at OTF.

What I'd change

  • Feedback loop into the KB. Right now the engineer edits the draft RCA and ships it — but those edits don't flow back into the knowledge base. The next iteration captures the final-published RCA as a new KB entry, closing the loop so the system gets sharper as it's used.
  • Retrieval quality eval, not just generation quality. Most LLM-tool benchmarks measure the final output. For an agent like this, the more interesting evaluation is whether the retrieval step pulls the right precedents. A small held-out set of incident pairs (known similar / known unrelated) would let me measure retrieval directly and decoupled from the LLM.
  • Per-service routing. An incident on the payment service has different relevant precedents from an incident on the email-delivery service. A smarter retriever would scope the search by service or by the org's service topology, not just by raw vector similarity.
