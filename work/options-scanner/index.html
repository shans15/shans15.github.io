Options Scanner — invert the firehose. Direction first, contracts second.

Most option scanners evaluate every contract on every ticker and try to sort the noise afterward. This one inverts the problem — find the directional setup on the daily chart first, then run the expensive contract math only on the survivors.

universeS&P 500 cadenceend-of-day stackPython · GARCH · Monte Carlo · Streamlit repogithub.com/shans15/options-scanner

Problem

Public options scanners are loud. They rank every available contract on every ticker by some composite of liquidity, implied vol, theta, and a few other terms, and present you with a multi-thousand-row spreadsheet. The signal-to-noise ratio is terrible. Most of the contracts the scanner ranks highly are sitting on top of charts that aren't actually setting up to move in either direction — the math is good, the underlying isn't.

From the repo, in my own words: "Most option scanners are noisy because they evaluate every contract on every ticker, then try to sort the firehose. This one inverts the problem."

Constraints

  • Single laptop, single-user. No data infrastructure. The scanner has to run end-of-day in under a minute against a 500-ticker universe on consumer hardware.
  • Read-only. No order execution. The scanner outputs a labeled candidate list; a human decides whether to trade.
  • EOD, not real-time. The detectors operate on completed daily bars. This is a swing/day-trade scanner, not a high-frequency signal generator. The cadence constraint is what lets the model use slow-but-correct setups instead of fast-but-noisy ones.

Approach

The scanner is the cleanest expression of Signal → Rank → Explain in any of my repos. Each stage has its own job and refuses to do the others' work.

01 / Signal — four technical detectors, run cheaply, drop most of the universe

A ticker only enters the scan if at least one of four Saty-style setups fires on its daily chart:

  • Compression breakout — Phase Oscillator squeeze with a stacked EMA ribbon, expanding range
  • Pullback in trend — price taps the 13/21 EMA in a stacked trend with PO near zero
  • Stage 2 breakout / Stage 4 breakdown — fresh EMA48 cross after compression, near a 52-week extreme
  • Failed-breakdown reversal — recovery above a swept low

The detectors are fully deterministic — no model calls, no embedding lookups, just price/EMA/PO arithmetic. Their job is to fail loudly: most tickers exit the pipeline here. The expensive option-chain pull never happens on the noise.

02 / Rank — strategy is chosen by the setup, then scored four ways

The crucial design choice: the surviving setup constrains the strategy. Bullish setup → only long calls and cash-secured puts. Bearish setup → only long puts and naked calls. You don't waste analysis on contracts the setup doesn't support. This is the inversion in action — the firehose never gets sorted; it gets defined out of existence by the upstream filter.

For every surviving contract, four probability-of-profit models run, each with a different prior on volatility:

  1. Black-Scholes baseline
  2. GARCH-conditioned forecast vol
  3. Monte Carlo on the GARCH path distribution
  4. Stress-tested adverse-move scenarios (1σ and 2σ against the trade)

The composite score is EV-aware — it doesn't reward high P(profit) on contracts where the expected loss in the failure case wipes the expected gain. The result is a small ranked list per ticker, not a sorted-by-IV firehose.

03 / Explain — labeled output, traceable to the setup

The scanner output is a 3-class label per ranked contract:

TRADE · WATCHLIST · NO_TRADE

Each row carries the setup name that put the ticker on the list, the strategy implied by that setup, the composite score, and the contract identifiers. The trader doesn't have to reconstruct why the scanner picked a contract — the upstream provenance is in the row.

Why this is the cleanest articulation of the methodology

Every project on this site applies Signal → Rank → Explain. The Options Scanner happens to articulate it in its own README, in my own words, against a problem (options screening) where the inverted-pipeline approach is unusually contrarian. Most scanners do it the other way. Most ML pipelines do it the other way. The fact that this one doesn't is what makes it interesting to point at when explaining how I think about systems.

If you want to understand the methodology from a single example, this is the one.

What I'd change

  • Setup-detector calibration on the meta-model. The four detectors are tuned individually. A meta-layer that re-weights them based on rolling per-detector forward-return performance would let the scanner learn which setups are working in the current regime without retraining the detectors themselves.
  • Per-ticker risk budgets in the composite score. Right now the scoring is contract-local. A portfolio-aware view would penalize correlated TRADE labels (e.g., five bullish setups all in the same sector on the same day) and surface the diversification picture.
  • A real backtest harness with walk-forward evaluation. The current evaluation is a 90-day historical replay (see output/backtest/scanner_90d_*.csv in the repo). Walk-forward with held-out test windows and a documented benchmark would convert the scanner from "I think this is working" to "here's the realized lift versus a naive long-call baseline."
